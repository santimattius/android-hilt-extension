# Limitations and known constraints

What Hilt Trace and the coroutine helpers do not cover, and which claims lack proof. Each item names its evidence. Items marked **unverified** are expected from the design but not backed by a test or a run in this repository. Related: [Setup](SETUP.md), [Tracing](TRACING.md), [Coroutines](COROUTINES.md).

## Not instrumented

Confirmed against Hilt 2.60.1 output.

| What | Why |
|------|-----|
| Unscoped bindings built inline inside a component accessor | Dagger inlines them; only the accessor section covers them. If something requests a `Provider<T>`/`Lazy<T>` of the binding, it gets a `SwitchingProvider` case and a `hilt.create` section. The sample's `provideAudience` is `@Singleton` for this reason. |
| `@Binds` | **No hook, not planned.** Dagger generates no factory, no `provideX`, no `SwitchingProvider` case and no call site for it: a request compiles to the implementation's own construction. Evidence: the read-only spike of issue #70 on Hilt 2.60.1 (generated sources and `javap` of the transformed classes; not a committed test). Not checked on Hilt 2.59.2. |
| `@Binds @IntoSet` / `@IntoMap` contributions and the aggregate `Set`/`Map` | **No hook, not planned.** A `@Binds` contribution is an inline `new Impl()` inside `Collections.singleton*`, and the aggregate has no code of its own (its generated method names are not stable). A contribution that is scoped, or requested as a `Provider`, gets a `SwitchingProvider` case and is already traced as `hilt.create`. Evidence: issue #70 spike, Hilt 2.60.1. A second read-only spike (issue #86, Hilt 2.60.1, `fastInit` on; a `@Provides @IntoSet` and `@IntoMap`, scoped and unscoped, requested as `Provider<Set<T>>`, `Provider<Map<K, V>>` and `Map<K, Provider<V>>`; not committed) found no `SetFactory`, `MapFactory` or `MapProviderFactory`: the set or map as a whole is a `SwitchingProvider` case that calls an instance `...Builder()` method (`SetBuilder`/`MapBuilder`), which has no `NEW` or static factory call to name it, so it is not traced and nothing is warned. An unscoped `@IntoSet` contribution is inlined in the builder and has no section, and several contributions of one type share one slice name. The transformed classes were consistent: only the entry-point accessor changed, no class was broken and nothing was traced twice. What Dagger generates for multibindings with `fastInit=false` was not checked. |
| A per-binding span around an inline `new X()` | **Not feasible.** A try/finally around `NEW ... <init>` leaves an uninitialized reference on the operand stack (a verifier hazard) and a span without a handler leaks when the constructor throws, which would break the fail-open guarantee. Evidence: issue #70 spike (reasoning over the generated bytecode; no such transform was written or run). |
| The static `provideX` call inside an accessor | **Not implemented.** Wrapping only the `provideX` call would be clean, but the value is low (the accessor section already covers it) and the outermost creation of a `SwitchingProvider` case would have to be excluded to avoid double tracing. Evidence: issue #70 spike, Hilt 2.60.1. |
| The router `get()` of a `SwitchingProvider` | Not traced. |
| A plain `Provider.get()` / `Lazy.get()` in user code is not linked to its requester | The router `get()` of a `SwitchingProvider` receives only an `id`, so generated code cannot identify the caller; automatic linking is not possible without user code, and the `hilt.create` slice of a plain `get()` is a root slice on the thread that ran it. It is linked if you call `Provider.getTraced(name)` / `Lazy.getTraced(name)` at your call site, which opens a `hilt.resolve` section named by you around the `get()` on the same thread. The adapters `Provider.suspending` and `Lazy.await` are linked the same way. Evidence: a read-only spike of the generated code, `DeferredResolutionTraceTest` (adapters) and `TracedGetTraceTest` (`getTraced`, debug and minified, Android 15 emulator). Issue #84. |
| `DoubleCheck` cache hits | Only the first creation of a scoped binding has a section (`TraceCaptureTest.aSingletonIsCreatedOnceNoMatterHowOftenItIsRequested`). |
| Constructor arguments of a created object | One section per case; no sections for the arguments. |
| `*_MembersInjector.injectMembers` | **Opt-in, off by default** (`hiltTrace { traceMembersInjectors.set(true) }`, see [Tracing](TRACING.md#members-injectors-opt-in)). The component never calls it (it calls the static setters), so only code that receives a `MembersInjector<T>` through DI and calls it records a `hilt.inject` section `<T>.injectMembers`. Field and method injection done by the component, and `@AndroidEntryPoint` classes, are not affected. Verified on Hilt 2.60.1 (`MembersInjectorTraceTest`, `MembersInjectorRuleTest`); **unverified** on Hilt 2.59.2. |
| Release variants | Unchanged by design (`ReleaseUnchangedTest`). |

## Build and environment

| Constraint | Evidence |
|------------|----------|
| Application module only; the plugin registers on `com.android.application`. | `HiltTracePlugin`. |
| Hilt `fastInit` must stay on (Hilt's default). With `-Pdagger.hilt.fastInit=false` Hilt generates no `SwitchingProvider`: creation sections are skipped and one warning is logged. | `HiltTracePlugin`, `PluginWiringTest`. |
| Coupled to the shape of Hilt-generated classes (verified on 2.60.1). An unknown shape, a method near 64 KB, or any error leaves the class unchanged with one warning. The supported range is exactly the `compat.yml` matrix (Hilt 2.59.2 and 2.60.1; see [Supported toolchains](SETUP.md#supported-toolchains)). New releases are noticed by the weekly `compat-latest.yml` run (first run pending until it has run on `main`) and the monthly Dependabot PR, so one can go unnoticed for up to a week or a month; a red run shows the consumer build or dex check failing, not every shape change. | `FailOpenTest`, `ASM` tests on captured output, `compat.yml`, `compat-latest.yml`, `scripts/check-supported-versions.sh`. |
| A library needs `ksp(hilt-trace-compiler)` and `hiltTrace.module`, or its entry points are not instrumented. The build passes either way. | `LibraryInstrumentationTest`, `StaleCatalogueTest`. |
| With real Hilt 2.60.1 and KSP, a library module's binding is instrumented in the app's debug dex (`hilt.create`; none in release). For an Android library project the catalogue reaches the app transform: the slice is named `fixture.lib.LibService` (not the bytecode name) and the `@EntryPoint` accessor is traced (`SingletonComponent.libService`) in debug, neither in release. An Android library does not package KSP resources, so the plugin reads the library's `generated/ksp/<variant>/resources` in place, in a task (`hiltTraceLibraryCatalogues<Variant>`) that runs after the library's compilation and therefore after its KSP task. | `RealHiltLibraryTest` (run with `./gradlew -p hilt-trace-gradle-plugin test --tests '*RealHiltLibraryTest'`), `LibraryInstrumentationTest`. |
| The Android library variant read is the one Gradle **selected** for the app variant, taken from the attributes of the resolved runtime variant (AGP's variant-name attribute, or the build type of a library without flavors), not assumed equal by name and not parsed from a configuration name. An app-only product flavor (`freeDebug` against the library's `debug`) reads the library's `debug` catalogue: its real slice names are in the app `freeDebug` dex and nothing is warned. The selection is read when the collector task runs, not while the task graph is built (that earlier approach made Gradle report the runtime classpath as resolved at configuration time). A library that has KSP-named tasks but none for the selected variant is skipped with one warning and the build passes; this is exercised only with a hand-registered KSP-named task (whether AGP with KSP creates a KSP task for every variant is not shown). A library from an **included build** is read too: its project directory is its build's directory plus its project path, and its `build` directory is assumed to be the default. Its KSP tasks are not visible to this build, so it never gets the missing-variant warning. If the resolved library artifact is not under that conventional `build` directory (a relocated project or build directory), the library is skipped with one warning naming it and its slices keep the bytecode names; the relocated output is not read (`MixedLibrariesTest`, relocated `layout.buildDirectory`; a relocated project directory takes the same check but has no test of its own; the check runs before the JVM and non-Hilt skip, so a JVM or non-Hilt library of an included build whose `build` directory is relocated also gets that warning, which is noise and not a skipped catalogue). A library is always read from the project of its own build (matched by the build identity of the resolved component, never by project path alone): a library of a build **nested** in an included build is not located, so it is skipped with one warning naming it (its slices keep the bytecode names) and the same-path project of the app's build is never read. The catalogues of all libraries share one output directory; two libraries that declare the same `hiltTrace.module` write the same file name, so the library that sorts first by build and project path keeps the plain name and the later one is copied under a distinct `~2` name, both are read, and one warning names both libraries. If the selected variant cannot be read from the attributes of an Android library (it has flavor attributes but no variant-name attribute), it is skipped with one warning; only the attribute reading is unit-tested (`LibraryVariantAttributesTest`), the warning itself is not reached by a real AGP build. JVM project dependencies are recognised by the absence of the Android build-type attribute and skipped silently: `java-library` is covered by `LibraryVariantTest`; `kotlin("jvm")`, a Kotlin Multiplatform `jvm()` target and an AGP Kotlin Multiplatform Android library were also checked by hand in an independent review (no warning, no crash) but have no committed test. The variant of a flavored library is read from `VariantAttr`, an attribute that AGP keeps in an internal package (`com.android.build.gradle.internal.attributes`; present in AGP 9.1.1 and 9.5.0, not deprecated, but not supported API): if a future AGP renames it, a flavored library is skipped with one warning, while a library without flavors still works because it falls back to the public `BuildTypeAttr`. A library with its own flavor dimension that the app does not have (`missingDimensionStrategy`) or matches by another flavor name (`matchingFallbacks`) reads the catalogue of the library variant Gradle selected, and only that variant's slice names are in the dex (`LibraryFlavorDimensionTest`, one dimension, two library variants with different bindings). A build with a current-build library, an included-build library and an app-only flavor stores and then reuses the configuration cache and finds the same slice names, with no configuration-time-resolution warning (`MixedLibrariesTest`). A library with **two** flavor dimensions (`tier` x `env`, the app choosing both with `missingDimensionStrategy`) is read like one with a single dimension: the app `debug` variant selects `freeStageDebug`, only that variant's slice names are in the dex and nothing is warned (`LibraryTwoFlavorDimensionsTest`, AGP 9.5.0, one fixture; more than two dimensions or `matchingFallbacks` across two dimensions were not tried). **Out of scope:** an older AGP whose variants lack the variant-name attribute. The supported range is exactly the `compat.yml` matrix (AGP 9.1.1 and 9.5.0 are the ones that were exercised), so such a flavored library would be skipped with the warning above and that case is not tested. | `LibraryVariantTest`, `RealHiltLibraryTest`, `NestedIncludedBuildTest`, `CatalogueCollisionTest`, `MixedLibrariesTest` (current-build library, included-build library and an app-only flavor together), `LibraryFlavorDimensionTest`, `LibraryTwoFlavorDimensionsTest`, `LibraryVariantAttributesTest`. |
| A Fragment is traced as `hilt.inject` `<Fragment>.members`, shown with the sample's `DemoFragment` on an Android 15 emulator and on the CI managed device (API 34). A nested child Fragment and a `DialogFragment` are shown too (`FragmentShapesTraceTest`: one `hilt.inject` slice each, siblings of their parent's and host's slices). An `@AndroidEntryPoint` BroadcastReceiver (`BroadcastReceiverTraceTest`) and `hiltViewModel()` from Compose, plain and with `SavedStateHandle` (`HiltViewModelTraceTest`), are shown on the same device. Navigation-scoped ViewModels (back stack entry store) are **unverified**. A retained `@AndroidEntryPoint` Fragment is not supported by Hilt itself: a spike on Hilt 2.60.1 saw `IllegalStateException: onAttach called multiple times with different Context! Hilt Fragments should not be retained.` (not part of a committed test). | `FragmentTraceCaptureTest`, `FragmentShapesTraceTest`, `BroadcastReceiverTraceTest`, `HiltViewModelTraceTest` (instrumented), `InjectRuleTest`. |
| Assisted creation (`@AssistedInject` with its `@AssistedFactory`) is traced as `hilt.create` named after the assisted class, with its dependencies nested; shown on a real Hilt graph in the sample on an Android 15 emulator. The rule is coupled to Hilt's shape (verified on 2.60.1 with `fastInit` on): the factory is an anonymous `$SwitchingProvider$N` whose `create` is straight-line code; any other shape is left unchanged with one warning. `@HiltWorker` uses the same generated shape but is **not verified end to end** (no WorkManager in the sample); it is covered by the shared rule and its ASM test only. | `AssistedCreationTraceTest` (instrumented), `AssistedFactoryRuleTest`, `ClassFilterTest`. |
| KSP only; there is no kapt path. | Project constraint, `CatalogueProcessor`. |
| `minSdk` 24 for the library modules and the sample. `androidx.tracing` 2.0.5 itself declares minSdk 23 (its AAR manifest), but that is not the library's floor: a consumer with minSdk 23 is rejected by the manifest merger (`uses-sdk:minSdkVersion 23 cannot be smaller than version 24 declared in library hilt-trace-runtime`), observed locally with AGP 9.1.1 / Kotlin 2.2.21 / Hilt 2.60.1, and the `minSdk 23` entry of the compat matrix passed in CI on that expectation. **Evidence-only probe (not support):** with the check overridden only in a throwaway consumer (`tools:overrideLibrary` in `compat/consumer/src/probe`, minSdk 23; the libraries and their minSdk 24 are untouched), the debug app and its smoke-test APK assemble locally and both report minSdk 23 (`apkanalyzer`). Observed in CI on PR #61 (job `api23-probe`, `reactivecircus/android-emulator-runner`, Android 6.0 / API 23 x86 `default` image): 3 tests, 0 failures, 0 skipped. With the override, the consumer's Hilt application starts, an activity instrumented by the plugin starts and injects, `SuspendLazy` from `hilt-coroutines-runtime` resolves a value, and the device reports API 23 (`expectedSdk=23`). The first run of that job failed because the action runs each `script` line in its own `sh -c`, which dropped the probe variables. A Gradle Managed Device is not an option for this, AGP documents them for API 27+. **Out of scope:** that a trace slice is recorded on API 23 (the smoke asserts none) and any other image: the published minSdk is 24, so the probe stays evidence and nothing is claimed about API 23. This is evidence, not support: the published minSdk stays 24. | `gradle.properties`, `compat/run.sh` (`COMPAT_EXPECT_MIN_SDK_REJECTION`, `COMPAT_API23_PROBE`), `.github/workflows/compat.yml`. |
| Hilt 2.59.2 (the older supported Hilt) is **unverified** for the shapes in the "Not instrumented" rows (multibindings, `@Binds`, assisted creation, members injectors, the accessor section). The `compat.yml` consumer job runs on 2.59.2, but its consumer has one `@Singleton @Inject` class and one `@AndroidEntryPoint` activity and `compat/check-dex.sh` only counts `HiltTrace.begin` call sites (debug above 0, release 0): it proves the build, the transform and the dex check run on 2.59.2 and that something is instrumented, not which slices, nor that those shapes are recognised or left unchanged. It cannot be run locally with the sample: its Kotlin 2.4 metadata makes the Hilt 2.59.2 compiler fail (the compiler reads metadata up to Kotlin 2.3). | `.github/workflows/compat.yml`, `compat/check-dex.sh`, `compat/consumer`. |
| Validated versions are listed in [Setup: Supported toolchains](SETUP.md#supported-toolchains). Others are unverified. | `gradle/libs.versions.toml`, `.github/workflows/compat.yml`. |

## Runtime

| Constraint | Evidence |
|------------|----------|
| With a category disabled, `HiltTrace.begin` returns `null` and allocates nothing; the call site still runs in instrumented builds. Measured once, by hand, on one physical moto g05 (Android 15, `speed`-compiled, charging, 29 C; five runs of `:benchmark-micro`): the baseline call takes about 4.6 ns and the same call with `begin`/`end` around it and the category disabled about 24 to 25 ns in three runs and 33 to 35 ns in two noisier ones, so about 20 ns more per traced call (up to about 31 ns). The two noisy runs also showed maxima of 574 and 756 ns and about 0.07 allocations per iteration that were not attributed; the three clean runs allocated nothing. It is a synthetic call path with the shape of the generated code, on one device. On the same device, the cold start of the `minified` sample with and without the instrumentation differed by 2 ms in the medians (407.5 against 405.5 ms, 24 starts each, IQR about 12 to 13 ms), which is within noise; the instrumented dex is 3,800 bytes larger ([Benchmark](BENCHMARK.md), "App start"). The `benchmark-smoke` CI job (passed on PR #60: 2 tests, 0 failures) only shows that it runs on an emulator with `EMULATOR,NOT-AOT-COMPILED` suppressed; emulator timings are not a measurement. | `HiltTraceTest` (disabled-category behavior), `CallPathsTest`, `:benchmark-micro` (manual run, 2026-11-15, not CI). |
| `begin`/`end` must run on one thread in one synchronous method and nest strictly (LIFO). The instrumented code satisfies this; manual use must too. | `HiltTrace` KDoc. |
| The system trace bridge (`HiltTrace.setSystemTraceEnabled(true)`) is opt-in and off by default. With it off, `begin` costs one extra volatile read and allocates nothing more. With it on, each traced call pays a system trace check and, during a session, a platform call; a system-only section allocates nothing, a section that is also in the tracer allocates one small token. The system label is `<category> <name>` (for example `hilt.inject MainActivity.members`), cut at 127 characters on the name side so the category prefix stays. Cost not yet measured: benchmark cases exist (`SystemTraceBridgeBenchmark`), but only an emulator run has happened, which is not a measurement; a physical-device run is pending. | `HiltTraceTest` (bridge tests, JVM fake of the platform trace). |
| Nothing records unless a driver enables the category. Without the `START` broadcast the automatic `tracing-wire` driver recorded nothing. | [Tracing](TRACING.md), run on an Android 15 emulator. |
| The application scope is never cancelled automatically; call `ApplicationScopeCloser.close()`. | `CoroutinesModuleUnitTest`. |
| `Provider.suspending` and `Lazy.await` cannot interrupt a `get()` that is already running; cancellation surfaces after it returns. | `BlockingResolutionDemoTest`, `SuspendProviderTest`. |
| A blocking `get()` of a heavy binding occupies a thread of the chosen dispatcher for its whole duration. Pick a dispatcher that can afford it. | Follows from the above; not separately tested. |
| `SuspendLazy` runs the initializer in the context of the caller that holds the lock. | `SuspendLazy` KDoc. |
| `traceCoroutine` writes a suspended coroutine as several thread segments of the same named section. | `TraceCoroutineTest`. |
| `@MainDispatcher` is `Dispatchers.Main`; JVM unit tests need `Dispatchers.setMain` or a replacement module. | `CoroutinesModule`. |

## Release and R8

- Release classes are not instrumented. With minification off the sample's release dex still holds the unused `HiltTrace` classes.
- The sample's `minified` build type (debug-like, instrumented, `isMinifyEnabled = true`) keeps the instrumentation under R8 with no extra keep rules: `./gradlew :app:verifyMinifiedTracing` finds the `hilt.inject`/`hilt.create` categories and the slice names (activity, fragment, view, service, ViewModel) in its dex. R8 inlines `HiltTrace` into the call sites and removes the class, so a keep rule for it is not needed. Without a tracing driver (`tracing-wire`) on that variant R8 dropped the call sites, so a minified build that should record needs the driver. Evidence: `verifyMinifiedTracing`, run once on the sample.
- The instrumented tests can also target the minified build type (`-PtestBuildType=minified`, task `:instrumentedTestsMinifiedCi`, CI job `instrumented-minified`), with test keep rules in `app/proguard-test-rules.pro` that apply only to that run. Observed on the CI managed device (`ci`, API 34, `aosp-atd`), PR #59, job `instrumented-minified`: 30 tests, 0 failures, 0 skipped (`TraceCaptureTest` 13, `MainActivityDemoTest` 13, `DemoScreenTest` 3, `FragmentTraceCaptureTest` 1), so the minified, instrumented APK records its slices at runtime (the slice assertions of `TraceCaptureTest` and `FragmentTraceCaptureTest` pass under R8). It took three CI runs. The first was a **false green**: Gradle finished successfully, but the result XML held a single `testRunFailed` testcase ("Instrumentation run failed due to Process crashed") and no test ran; `scripts/assert-instrumented-results.sh` now fails the job in that case (no result XML, 0 testcases, any failure or error, or a `testRunFailed`). The crash came with the test dex referencing 143 library types (Compose, `androidx.tracing`, Kotlin) that R8 had removed from the app; keeping those packages in the test rules let the 30 tests start. The second run failed 2 tests with `NoSuchMethodError` (`FragmentManager.findFragmentByTag`, `DemoSpec.getId`), fixed by keeping `androidx.fragment` and `DemoSpec`. **Limits:** the test rules keep whole packages, so this shows that the instrumented call sites record under R8, not how much R8 shrinks a production build; the run is on one image (API 34); `hilt-coroutines-runtime` is not minified.
- **Minified release stays uninstrumented (CI check, first CI run pending).** The default release is `isMinifyEnabled = false`. Passing `-PminifyRelease=true` turns R8 on for release only, and `./gradlew -PminifyRelease=true :app:verifyMinifiedReleaseUntraced` (CI step in the `build` job) fails unless the R8 mapping exists and the release dex has 0 `HiltTrace;.begin` call sites and 0 `androidx/tracing` references. Observed locally: the script goes red on the instrumented `minified` APK (45 `androidx/tracing` references) and green on the minified release APK (0 and 0, mapping 174198 lines). This is a dex check, not a runtime measurement.
- **Manual device evidence (2026-11-15, not CI).** With R8 on for release, `:app:assembleRelease` succeeded (mapping about 174k lines); the dex had 0 `HiltTrace;.begin` call sites and no `androidx/tracing` references (the only `hilt.inject`/`hilt.create` strings were the 9 UI texts of the sample). Signed with the local debug keystore and installed on one physical moto g05 (Android 15, API 35, arm64): start in about 634 ms, not debuggable, 300 random monkey events with no crash, and every demo card's Run button gave the expected result (activity, ViewModel and view injection, scoped singleton `same instance: true`, qualified dispatchers including `@MainDispatcher` = main, SuspendProvider, SuspendLazy, cancellation, complex graph) with the process still alive. **Limits:** one manual run on one device; the sample only, not a consumer with its own R8 rules; debug-signed; the run-time absence of slices was inferred from the dex, not measured.
- **Out of scope (not provable from this repository):** a minified release of a consumer app with its own R8 rules, other devices or API levels, and run-time absence of slices in release. What is claimed is limited to the dex check `:app:verifyMinifiedReleaseUntraced` on the sample and the one manual device run above; nothing is claimed beyond them.

## Publishing state

- The four artifacts and the Gradle plugin marker for `1.0.0-alpha01` are available from Maven Central. The marker is `io.github.santimattius.android.hilt.trace:io.github.santimattius.android.hilt.trace.gradle.plugin`; a marker's group is the plugin id, so it sits under the verified `io.github.santimattius` namespace.
- Instrumented tests need a device or emulator. The `instrumented` CI job runs them on a Gradle Managed Device (`./gradlew instrumentedTestsCi`); its first CI run passed on PR #56: 34 tests, 0 failures, 0 skipped on the `ci` device (API 34, `aosp-atd`), including `FragmentTraceCaptureTest`. The `build` job compiles and packages them. **Known flake, immediate cause found, origin not established (issue #74):** `TraceCaptureTest.complexGraphShowsTheChain…` timed out four times in about twenty-five managed-device CI runs (twice in the minified job, twice in the debug job); each time it passed on a rerun with the same code. The first failure with the richer message added in PR #63 reported 51 slices (25 begin, 26 end, balanced=false), the expected-slices predicate true and 9.4 s without a change: the capture had settled but held one END more than BEGINs, and `awaitSettled` only returns when both counts are equal, so it cannot finish however long it waits. That is why raising the wait to 30 s did not help and was reverted. Where the extra END comes from is not established; work left over from an earlier test that closes a section after the new sink was installed is a hypothesis that nobody has verified. An earlier note here blamed an emulator stall; the logs do not support it and it is withdrawn. The results guard still fails the job in that case, which is intended: a failed test is never reported as a pass.

## Compose preview workaround

With AGP 9.5.0 and the Compose compiler plugin of Kotlin 2.4.21, the sample needs two settings for `:generateDebugComposePreviewRunfiles` (see `app/build.gradle.kts`). The failure is independent of Hilt Trace. Each half is checked to still be required: dropping either one (`-PdisableComposePreviewWorkaround=resources|unit-tests`) makes AGP 9.5.0 fail creating the task, while the control with both in place does not. `app/scripts/check-compose-preview-canary.sh` (CI job `compose-preview-canary`) exits 1 when a dropped half no longer fails, so the workaround can be removed. Observed locally on AGP 9.5.0 / Kotlin 2.4.21, and the CI job passed on PR #56. Details: [Setup](SETUP.md#application-module).
